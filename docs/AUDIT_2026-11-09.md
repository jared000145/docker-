# Audit RectorPlus — 9 novembre 2026

## Décision proposée

Conserver l’application React/Vite, Supabase et le projet Capacitor. Procéder par
lots vérifiables, en commençant par une interface commune et les photos de profil,
puis la fiabilité des services. Les trois images fournies servent de référence
visuelle pour les espaces connectés ; leurs noms, photos, chiffres et graphiques
ne doivent pas devenir des données réelles de la plateforme.

Cet audit ne modifie ni le code applicatif, ni le schéma, ni la production.
Seuls ce rapport et les sorties locales des contrôles sont ajoutés.
Il s’agit d’un audit technique initial, pas d’un test d’intrusion ni d’une
certification de conformité. Tous les modules métier n’ont pas été exercés avec
des établissements réels et des jeux de données complets.

## 1. Architecture et technologies

| Couche | Existant observé |
|---|---|
| Web | React 18, TypeScript, Vite 5, React Router 6 |
| Interface | Tailwind, composants Radix/shadcn, Lucide, Framer Motion |
| Données et cache | Supabase JS, TanStack Query, abonnements Realtime |
| Graphiques et documents | Recharts, jsPDF, PDF.js, SheetJS/xlsx |
| Backend | Supabase PostgreSQL, Auth, Storage, fonctions Edge Deno |
| Hébergement | Vercel ; domaine rectorplus.com géré chez IONOS |
| Android | Capacitor 8, projet Gradle com.rectorplus.app |
| Tests | Vitest/Testing Library, tests SQL PGlite, tests de gardes Edge |

`src/App.tsx` définit les routes et les espaces par rôle. `src/hooks/useAuth.tsx`
gère la session et le profil. Les contrôles serveur, fonctions SQL et politiques
RLS complètent les routes protégées. `src/pages/admin`, `superadmin`, `professor`,
`parent`, `director` et `validator` regroupent les principaux espaces.

Le dossier contient aussi des intégrations Lovable héritées : elles ne sont pas
toutes compatibles avec le backend reconstruit. Ne pas les supprimer sans établir
la liste des usages et leurs remplacements.

Aucun dépôt `.git` n’a été trouvé à la racine lors de cet audit. Le workflow GitHub
présent ne constitue donc pas une preuve que le code est versionné à distance.
La mise en place d’un historique et de points de restauration est prioritaire.

## 2. État vérifié de Supabase

Lecture seule du projet `ruouwtuetbuyxwrpqzfc` :

- 106 tables publiques, toutes avec RLS activée.
- 398 politiques publiques, 119 clés étrangères et 220 index.
- 10 migrations appliquées.
- 14 fonctions Edge listées, toutes `ACTIVE`.
- Bucket `avatars` public, limite 5 Mo, sans liste de types MIME autorisés.
- Buckets `signatures`, `backups` et `preregistrations` privés.
- `preregistrations` limite les fichiers à 10 Mo et aux PDF/PNG/JPEG/WebP.

Ces compteurs ne prouvent pas à eux seuls l’absence de faille. Les tests locaux
vérifient plusieurs scénarios d’isolation, d’escalade et de cohérence ; ils ne
couvrent pas exhaustivement chaque combinaison de politique sur les 106 tables.

Les fonctions SQL sensibles étudiées utilisent des autorisations serveur ; les
transactions de création/validation évitent les établissements doublonnés dans
les scénarios testés. La règle `staff_role_read` existe dans la migration 005 et
en production : la lecture des rôles par le personnel du même établissement est
bien prévue. Aucun défaut de compteur fondé sur l’absence de cette règle n’est retenu.

## 3. Frontend et rendu des références

Les captures montrent une identité cohérente : navigation bleu nuit, sélection
bleue, surfaces très claires, cartes arrondies, tableaux structurés, graphiques
bleus/violets, profil visible et barre supérieure avec recherche/notifications.

Le projet possède déjà la plupart des primitives nécessaires. Les couleurs et
espacements sont toutefois dispersés entre plusieurs layouts et styles hérités.
Les zones enseignant, parent et super administrateur n’ont pas toutes les mêmes
éléments de compte. Le tableau de bord administrateur comporte déjà des requêtes
et graphiques : il faut réutiliser ses données et adapter sa présentation.

La recherche globale est présente dans l’interface, mais ses dépendances backend
doivent être vérifiées avant d’en faire un élément central du nouveau bandeau.
Un champ visuellement actif ne doit pas masquer un service absent.

Le site public doit rester cohérent avec cette charte, tout en conservant son
objectif de présentation et sa photo d’accueil. Ne pas transformer l’accueil
marketing en tableau de bord ni modifier son parcours d’inscription sans raison.

### Contrat visuel proposé

- Barre latérale d’environ 260–280 px sur ordinateur, tiroir sur mobile.
- Logo RectorPlus et identité de l’établissement, sans renommer tous les clients
  « Université RectorPlus ».
- Carte de compte avec photo réelle, nom et rôle ; accès direct à « Mon compte ».
- Bandeau supérieur commun avec commandes réellement disponibles.
- Quatre indicateurs métier selon le rôle, suivis de graphiques et tableaux.
- Une grille adaptative : quatre, deux puis une colonne selon la largeur.
- Cartes blanches, fond clair, bordures discrètes, contrastes et focus visibles.
- Chiffres calculés depuis la base ; absence de données explicitement présentée.
- Aucun nom ou portrait des références utilisé comme identité d’un utilisateur.

## 4. Photos de profil : existant et écarts

`ProfileSettingsPage.tsx` contient déjà un import dans le bucket `avatars` et une
mise à jour de `profiles.avatar_url`. `AdminLayout.tsx` affiche déjà cet avatar.
Cela ne suffit pas à valider un parcours universel :

1. L’import dépend de l’extension du nom du fichier et ne propose pas de recadrage.
2. Le bucket public ne limite pas les types MIME ; ne pas le présenter comme privé.
3. Le fichier est écrasé au même chemin, ce qui peut conserver l’ancienne photo en cache.
4. L’invalidation `['profile', user.id]` ne correspond pas au profil stocké dans
   le contexte Auth ; l’affichage dépend alors du retour Realtime ou d’un rechargement.
5. La page enseignant propose principalement la signature, pas un éditeur de photo.
6. L’import de `AdminSettingsPage.tsx` identifié est celui du logo d’établissement,
   qui ne doit pas être confondu avec la photo personnelle.
7. Le parcours de photo n’a pas été testé en production pendant cet audit.

### Solution proposée pour le premier lot

Un composant `ProfilePhotoEditor` et un menu de compte commun aux rôles. Import
JPEG/PNG/WebP, décodage réel, aperçu et cadrage carré, redimensionnement raisonnable,
gestion des erreurs et remplacement sans casser la dernière photo valide.
Mettre à jour explicitement le contexte de profil après confirmation du serveur.
Utiliser des noms de fichiers uniques pour éviter les anciennes images en cache.

Décider de la confidentialité avant déploiement : les photos personnelles,
notamment celles des mineurs, ne doivent pas devenir publiques par accident.
La cible recommandée est un stockage privé et un affichage autorisé. Son introduction
doit être additive, compatible avec les avatars actuels et testée avant migration.
Conserver les initiales lorsque l’utilisateur n’a pas ajouté de photo.

L’état `ACTIVE` d’une fonction n’est pas une validation de tous ses parcours.
Les droits par professeur, imports complexes, clôtures et calculs doivent être
exercés avec des jeux de données dédiés avant une commercialisation large.

## 6. Multi-établissements et campus

Le schéma contient établissements, campus, équipes et tables de rôles. Le profil
et le contexte courant restent principalement centrés sur un `institution_id`.
La sélection d’un campus ne prouve pas qu’un utilisateur peut avoir plusieurs
affiliations indépendantes ni plusieurs rôles simultanés dans plusieurs établissements.

La hiérarchie groupe → établissements → campus et le changement d’affiliation
doivent faire l’objet d’un plan de migration séparé : memberships explicites,
contexte actif, cache par affiliation et permissions serveur. Ne pas élargir
simplement les politiques RLS pour faire fonctionner le frontend.

## 7. Sauvegardes et restauration

Les écrans invoquent `backup-data` et `restore-from-drive`, absentes des 14 fonctions
actives. Les tables d’historique et le bucket `backups` ne constituent donc pas une
solution complète. Aucune restauration globale ou sélective n’a été prouvée.
Le niveau de sauvegarde/PITR du contrat Supabase n’a pas été vérifié dans le compte.

La documentation Supabase précise que la sauvegarde de base ne remplace pas celle
des fichiers Storage : https://supabase.com/docs/guides/platform/backups.

Prévoir un export base + objets + manifeste, une copie indépendante chiffrée, des
contrôles d’intégrité et une restauration dans un environnement isolé. Définir la
rétention et les responsables. Avant toute restauration sélective, calculer les
relations dépendantes et prévisualiser le résultat. Rien ne sera restauré en production
sans validation explicite. Ne pas annoncer de sauvegarde fiable sans test de restauration.

## 8. Signatures et cachets

Un import de signature existe et un traitement de fond est prévu. Le composant
observé enregistre une image encodée dans `profiles.signature_url`. L’interface
annonce une utilisation sur des documents, mais il n’existe pas encore de module
central démontré de cachets, de délégations, d’historique et de révocation.

Prévoir un stockage privé, le recadrage, une prévisualisation explicite avant usage,
les autorisations par service et la traçabilité du document final. Les mécanismes
de QR et de validation publique doivent être vérifiés, pas simplement dessinés.
Une image de signature ne doit pas être présentée comme une signature électronique
certifiée. Les exigences juridiques devront être étudiées selon les pays visés.

## 9. Android, Windows et indépendance des versions

- Projet Android présent : `com.rectorplus.app`, suffixe `.debug` pour les tests.
- `versionCode = 1`, `versionName = "1.0"` : convention 1.0.0 et historique à formaliser.
- `compileSdkVersion = 36`, `targetSdkVersion = 36`, minimum 24 dans le code.
- Workflow d’APK debug présent ; pas de preuve d’APK/AAB release signé et testé.
- Pas de configuration de signature release ni de Play In-App Updates démontrée.
- Pas de chaîne Windows native identifiée ; le site utilisable sous Windows n’est
  pas une application Windows installable validée.

Le mode Capacitor par défaut embarque `dist`. Le mode distant est explicitement
réservé aux tests. Pour respecter le document maître, le maintenir hors publication
Android officielle. Ne pas synchroniser Android à chaque publication web.
Le backend doit rester compatible avec les anciennes versions encore supportées.

Avant Google Play : compte développeur et exigences propres à ce compte, clé de
signature conservée, AAB release, tests appareils, permissions et liens, politique
de confidentialité, déclaration des données, visuels, fiche et piste de test.
La cible SDK correspond à l’exigence API 36 indiquée pour les nouvelles soumissions
à la date de cet audit, sans suffire à certifier le reste du dossier :
https://developer.android.com/google/play/requirements/target-sdk.

Les notifications OPTIONAL/RECOMMENDED/REQUIRED et leur configuration serveur
restent à construire. Utiliser les parcours officiels Google Play lorsque disponibles :
https://developer.android.com/guide/playcore/in-app-updates.

## 10. Dépendances et qualité

`npm audit --omit=dev` signale 9 entrées de paquets concernés : 5 de sévérité haute
et 4 modérée, aucune critique. Ce comptage inclut des dépendances transitives et
des outils classés dans les dépendances de production ; ce n’est ni un nombre de
failles indépendantes ni une preuve d’exploitation sur le site.

Paquets concernés : `@lovable.dev/mcp-js`, `@modelcontextprotocol/sdk`,
`@hono/node-server`, `vite`, `esbuild`, `react-router-dom`, `react-router`, `xlsx`, `zod`.
Plusieurs corrections proposées impliquent une version majeure ; `xlsx` ne présente
pas de correctif automatique dans ce résultat. Ne pas lancer `npm audit fix --force`.
Évaluer l’exposition, les chemins réellement utilisés, puis mettre à jour par lots testés.

Le lint porte sur 378 fichiers : 0 erreur, 2 175 avertissements. Les nombreux `any`,
variables inutilisées et dépendances de hooks justifient un assainissement progressif,
pas une réécriture générale pendant la refonte visuelle.

Certaines anciennes documentations annoncent encore « aucun cloud déployé » ou
105 tables/11 fonctions ; ces passages ne reflètent plus le relevé actuel ci-dessus.

## 12. Risques de régression et tests du premier lot

| Changement | Risque | Vérification nécessaire |
|---|---|---|
| Styles partagés | Casser un autre rôle ou un thème d’établissement | Captures et navigation des rôles sur ordinateur/mobile |
| Menu commun | Mauvaise destination selon le rôle | Étudiant, enseignant, parent, admin, direction, super admin |
| Photo privée | Casser les anciens avatars ou exposer les nouveaux | Lecture autorisée, expiration URL, remplacement, retour après reconnexion |
| Rafraîchissement profil | Photo d’un autre compte en cache | Connexion A → déconnexion → connexion B, onglets multiples |
| Graphiques | Afficher un succès fictif ou compter un autre établissement | Données vides, jeu connu, isolation entre deux établissements |
| Mise à jour de dépendances | Ruptures de route, validation ou imports Excel | Lots séparés, tests et retour à la version précédente |

Avant les changements : figer le code et les métadonnées utiles, établir un historique
Git et un moyen de retour arrière. Avant toute migration : sauvegarde adaptée et
restauration testée. Valider les captures locales avant publication.

Préparer localement le rendu des références pour le tableau de bord et les paramètres,
introduire un menu de compte et un éditeur de photo réutilisables, puis tester les rôles.

maître. Ne pas commencer les sauvegardes destructives, l’architecture multi-affiliations
